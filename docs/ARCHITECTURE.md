A Hebrew (RTL) Sudoku platform. Today it's a multi-language prototype, not a deployed app.

## Dataset Pipeline Architecture (Plan 1: lower tiers)

**Two-Zone Generation & Grading**

The dataset pipeline splits puzzle generation and grading into two independently-verifiable zones:

1. **Trusted Zone:** Docker container running qqwing (Debian distro package, immutable, no network).
   - Role: Generate random puzzles at the specified difficulty level; solve each one; count solutions (uniqueness gate).
   - Network isolation: `--network none` prevents any data leak or external communication.
   - Invoked via TypeScript wrappers: `generate(tier, count)` → puzzles; `solveAndCount(puzzles)` → solution + unique-count.

2. **Host Zone:** TypeScript orchestrator + Rust grader (both under repo control, open-source, auditable).
   - Role: Apply quality gates (symmetry, clue floor, dedup, schema validation); identify solving techniques (Rust grader); compute fun-score; assemble final records.
   - Checkpoint resumability: Per-tier JSONL append-only files allow recovery from interruption.
   - Output: JSON Lines format (`sudoku_lower.json`), one record per line.

This architecture ensures that **the puzzle source is provably isolated** (qqwing cannot bias the data or leak to external systems), while **technique grading** (which requires the full Rust ecosystem) runs in the host where we can trust the implementation end-to-end.

## Dataset Pipeline Architecture (Kaggle recalibration — 2026-07-03, current shipping path)

The `sudoku_150000.json` dataset does **not** generate puzzles — it *sources* them from Kaggle's "3-million-sudoku-puzzles-with-ratings" (radcliffe) and re-validates/re-rates with the same trusted graders. Same two-zone trust model, extended to untrusted **data**:

1. **Fetch (sandbox, network on only here):** `sandbox/kaggle.Dockerfile` builds a minimal `sudoku-kaggle` image (curl/unzip/node). `kaggle-source.ts:fetchKaggleCsv()` downloads the 536 MB CSV via **Bearer/KGAT token** into a Docker **named volume** `kaggle-csv` — the raw file never touches the host FS. SHA pinned in `sandbox/kaggle.lock`.
2. **Filter (sandbox, `--network none`):** `kaggle-filter-cli.ts` streams the CSV in-container, buckets rows into per-tier candidate pools by (clues, difficulty) via `kaggle-filter.ts:prefilterTiers()` (bands **may overlap** — a puzzle can be a candidate for medium *and* hard), and writes a small candidate JSONL to the host. Only 81-char puzzle strings + ids cross back.
3. **Validate / re-rate (existing graders):** `kaggle-pipeline.ts:buildKaggleTier()` runs qqwing (uniqueness, trusted solution), the Rust grader (lower-tier technique classification), and **serate** (hard-tier ER, sandboxed) over each candidate pool with a resumable checkpoint **+ cursor**. Accept gates: lower = Rust grade matches tier; hard = serate ER ∈ **[3.4, 4.5]** (the band *is* the no-guessing gate — no Rust solvable-gate for hard). Medium/hard are separated by the graders, not the band.
4. **Assemble:** `assemble.ts:assembleKaggle()` cross-tier dedupes, sorts, assigns sequential `id` 1…N, writes `sudoku_150000.json` (gitignored). Entry point: `bin/run-kaggle.ts` (`--calibrate` = per-tier accept-rate report + samples, the owner gate; `--count N` = smoke; no arg = full build).

Key finding: the Kaggle set is **bimodal** (puzzles are either straightforward or jump to obscure), so "fair-hard" is scarce — the tiers were tuned around that. See DECISIONS 2026-07-03.

## Puzzle-source generators (`scripts/` — 2026-07-04, `sudoku_150000.json` is the sole source everywhere)

`sudoku_150000.json` no longer just feeds a "future Supabase load" — it is the single input for every puzzle surface in both repos. Four deterministic, unit-tested (`node --test`) scripts read it directly (never a copy):

1. **`generate-seed.mjs`** — selects the 365 **daily** puzzles: 37 very_easy + 146 easy + 145 medium + 37 hard (10/40/40/10). Lower tiers ranked by `fun_score` DESC then `puzzle` ASC; hard ranked by `er_rating` ASC (gentlest — hard has no `fun_score`). Assigns `position` 1..365 via a deterministic even (Bresenham-style) interleave across the four tiers so difficulty varies day-to-day rather than running in blocks. Writes `sudoku_next/supabase/seed.sql`.
2. **`generate-cold-start.mjs`** — regenerates the 12-puzzle offline bundle `sudoku_next/app/lib/cold-start-puzzles.ts` (3 per DB tier, remapped to the app's difficulty labels: very_easy→easy, easy→medium, medium→hard, hard→extreme).
3. **`generate-sample-puzzles.mjs`** — regenerates root `puzzles.json` (15 puzzles, 5 each of easy/medium/hard), used only by the superseded `web/` prototype so it still builds.
4. **`load-supabase.mjs`** — streams all 148,206 puzzles into the live Supabase `puzzles` table via PostgREST (`on_conflict=puzzle`, `resolution=ignore-duplicates`, batches of 500), taking the service-role key at runtime (never committed). This **replaces** the deleted `generate-library.mjs` (used to build a committed 10k SQL library) and `upload_to_supabase.py`. Running it against the live database is a manual operator step — procedure in `sudoku_next/docs/RELOAD-RUNBOOK.md`. Migration `0010_interleave_daily.sql` is superseded by `seed.sql`'s interleaved positions and must not be re-run post-load.

App code and the Supabase schema/migrations were not changed by this work — the app already reads puzzles by difficulty (RPC `get_random_puzzles`) and the daily by `position` (RPC `get_daily_puzzle`); only the data feeding those tables/bundles changed.

## The big architectural issue — RESOLVED (Phase 3 v1)
The game used to be implemented **twice**: properly in `lib/sudoku-engine.ts`, and again (worse) as inline JS in `index.html`. As of Phase 3 v1, the new `web/` app plays exclusively through the engine — there is now one implementation. `index.html`'s inline logic is dead; the file remains only as a visual reference until parity is confirmed, then it gets deleted.
