# Dataset Pipeline — Sudoku 10,000 (Plans 1 + 2)

This pipeline generates the full four-tier Sudoku dataset: **very_easy** (2,000), **easy** (3,000), **medium** (3,000), and **hard** (2,000) — **10,000 total records** in JSON Lines, written to `sudoku_10000.json`.

- **Lower three tiers (Plan 1):** generated + uniqueness-checked by the trusted **qqwing** container, technique-graded by the Rust grader, rotational-symmetry enforced.
- **Hard tier (Plan 2):** generated by **HoDoKu** (technique-targeted) and difficulty-rated by **serate** (Sudoku Explainer ER), both run inside a no-network sandbox; every survivor is re-validated for uniqueness by the trusted qqwing container.

## What It Produces

Each record:
```json
{
  "puzzle": "...",           // 81-char string (0 = blank, 1–9 = given)
  "solution": "...",         // 81-char string (1–9, fully solved)
  "difficulty": "hard",      // very_easy | easy | medium | hard
  "techniques": ["x_wing"],  // lower tiers: Rust grader; hard: HoDoKu technique tags
  "givens": 25,
  "er_rating": 4.2,          // hard: serate ER (3.4–5.0). Lower tiers: null
  "fun_score": null,         // lower tiers: 0–5 score. Hard: null
  "generated_at": "2026-06-29T12:48:00Z"
}
```

## Prerequisites

1. **Docker running** (Colima or Docker Desktop). All tools run with `--network none`.
2. **Rust release build** (lower-tier grading):
   ```bash
   cd sudoku-generator && cargo build --release
   ```
3. **Trusted qqwing image** (lower tiers, one-time):
   ```bash
   ./dataset-pipeline/sandbox/build-qqwing.sh
   ```
   Builds `qqwing-trusted` (Debian Bookworm + apt qqwing 1.3.4).
4. **Sandboxed `sudoku-jars` image** (hard tier, one-time):
   ```bash
   ./dataset-pipeline/sandbox/build-jars.sh
   ```
   Multi-stage build that fetches + integrity-verifies the untrusted tools **entirely inside Docker** (nothing touches the host): HoDoKu 2.2.0 downloaded + SHA-256-verified, serate/SukakuExplainer cloned at a pinned commit + built from source. A wrong hash or a drifted commit fails the build (that is the security gate). Pins live in `dataset-pipeline/sandbox/jars.lock`.

## Smoke Run

```bash
node dataset-pipeline/bin/run-all.ts --count 10
```
Generates 10 per tier (40 total, well under a minute). Output → `sudoku_10000.json`.

## Full Run

```bash
node dataset-pipeline/bin/run-all.ts
```
Produces very_easy 2,000 · easy 3,000 · medium 3,000 · hard 2,000 = **10,000 records** → `sudoku_10000.json` (git-ignored). Observed runtime **~17 minutes** on a 2-CPU/2GB Colima VM (lower tiers ~7 min, hard tier ~10 min). Resumable — re-run the same command to continue from checkpoints.

> **serate is the hard-tier bottleneck.** It rates each candidate (~155 ms/puzzle on the 2-CPU VM) and only ~30% of HoDoKu candidates land in the ER 3.4–5.0 band, so the hard tier over-generates ~3× the kept count. Its container timeout scales per-puzzle (`SERATE_TIMEOUT_PER_PUZZLE_MS`); a slow batch is retried, not fatal.

## Output & Checkpoints

- **Final dataset:** `sudoku_10000.json` (repo root, JSON Lines). Plan-1-only output `sudoku_lower.json` is written by `run-lower.ts` and is separate.
- **Resumable checkpoints:** `dataset-pipeline/checkpoints/<tier>.jsonl` (`very_easy`, `easy`, `medium`, `hard`). Each batch is appended; on restart the pipeline loads them and resumes. Over-generates slightly, then trims to target.
- **Restart a tier:** `rm dataset-pipeline/checkpoints/<tier>.jsonl` then re-run.

## Architecture: Trust Zones

1. **Trusted zone — qqwing** (`qqwing-trusted`, immutable Debian build): generates lower-tier puzzles, and is the **independent uniqueness gate** (`count-solutions`) for ALL tiers — including re-validating the untrusted HoDoKu output.
2. **Sandboxed untrusted zone — `sudoku-jars`** (HoDoKu + serate): acquired/verified/run only inside Docker, always `--network none`. The host (TypeScript) only issues `docker build`/`docker run` via leak-safe named containers (see DP-2 below).
3. **Host zone — TypeScript orchestrator + Rust grader:** quality gates, technique grading (lower tiers), assembly, sorting, output.

### Container-leak safety (DP-2)
Every host-launched container is **named** (`qqwing-<uuid>` / `hodoku-<uuid>` / `sandbox-<uuid>`) and force-reaped with `docker stop -t 0 <name>` on every settle path. Under Colima, `--rm` alone is client-driven and orphans containers when the client is killed — the named force-stop is what actually reaps them. The shared runner lives in `dataset-pipeline/src/docker.ts` (used by the HoDoKu + serate wrappers); qqwing has the same pattern inline. Verified: 0 leaked containers across the full 10k run.

## Quality Gates

**Lower tiers (very_easy/easy/medium):** uniqueness (qqwing `count-solutions` = 1) → 180° rotational symmetry → clue floor (≥17, ≥18 if symmetric) → dedup → schema validation → Rust-grader technique/fun-score.

**Hard tier:** uniqueness (trusted qqwing over untrusted HoDoKu output) → serate ER band **3.4 ≤ ER ≤ 5.0** → clue floor → dedup → schema validation. **180° symmetry is NOT enforced for hard** — HoDoKu generates asymmetric puzzles (0/200 symmetric, measured), so enforcing it would yield ~0 (owner decision 2026-06-29; see `docs/DECISIONS.md`). Difficulty for hard comes from the serate ER number, not the Rust grader (which lacks the wings/chains those puzzles need).

## Troubleshooting

| Issue | Check |
|-------|-------|
| `qqwing-trusted` not found | `./dataset-pipeline/sandbox/build-qqwing.sh` |
| `sudoku-jars` not found | `./dataset-pipeline/sandbox/build-jars.sh` |
| `sudoku-generator --grade` missing | `cd sudoku-generator && cargo build --release` |
| Docker connection error | Ensure the daemon is running (`docker ps`) |
| Stray `qqwing-*` / `hodoku-*` / `sandbox-*` containers | Healthy runs leave none; clean with `docker ps -aq --filter name=hodoku- | xargs docker stop -t 0` |
| Checkpoint corrupted | Delete `dataset-pipeline/checkpoints/<tier>.jsonl` and resume |
| Hard tier yields slowly | Expected — serate is CPU-heavy and only ~30% of candidates are in-band; the checkpoint makes the long run safe |
